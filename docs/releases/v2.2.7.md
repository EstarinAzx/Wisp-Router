# Wisp 2.2.7 / companion VSIX 1.14.4

This patch restores supported Antigravity custom-model effort choices and adds an explicit opt-in Claude client compatibility option.

- Eligible tiered targets expose Low, Medium and High in the Desktop catalog. Responses forwarding preserves the selected literal value. Native model descriptors and unsupported-effort guards remain intact.
- `wisp antigravity-compat on|off|status` controls the shared option in both Bridge hosts. It defaults off and requires a new Claude conversation after changes.
- When enabled, positioned-system requests routed from Claude Messages to Antigravity receive the client's supported capability rejection before credential lookup or Provider dispatch. Claude performs its normal recovery; Wisp does not rewrite reminders.
- Fixed top-level instructions remain system instructions. Later reminders may become user context, and some feature-specific reminders may be omitted. Signed Desktop hoisting, protocol5, native forwarding and other Provider routes are unchanged.

Local tests with the actual Claude client establish a stable fixed instruction prefix and preserved prior content under the disclosed fallback. The bounded real-provider comparison halted on its first fallback response with a SAFETY finish. No cache improvement, historical plateau repair or general rejection rate is established. The compatibility option is experimental and remains off by default.

The current Desktop backend separately loads all three effort choices and retains High after catalog refresh and backend restart against synthetic upstream responses. This is backend evidence; it does not establish the interactive Desktop picker, installed VS Code host behavior or Provider-internal reasoning allocation. A separate actual-target effort check stopped when its first Low request returned HTTP 429; Medium and High were not sent. The response body and usage were not retained, so the cause, consumption and target acceptance remain unknown.
