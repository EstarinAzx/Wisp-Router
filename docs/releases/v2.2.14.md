# Wisp 2.2.14 / VS Code companion 1.14.11

This patch prevents an exhausted Antigravity model from diverting unrelated model requests to direct Anthropic.

## Fix

Previously, Wisp stored cooldowns for the whole Antigravity provider. A Gemini Carbon quota error could therefore put Antigravity Claude on cooldown too. Claude family requests then fell back to direct Anthropic, even when Antigravity Claude still had quota.

Quota cooldowns and repeated transient-failure streaks now use the resolved provider/model pair for Antigravity. Switching to another model or editing a family route reads the new target's own cooldown. Failures stay attached to the model actually dispatched when settings change during an in-flight request. Other providers retain their existing behavior. An explicit alias remains pinned; the same exhausted model still follows existing fallback rules, and its cooldown expires normally.

## Verification and limits

The source fix passed 2,166 core tests, 215 terminal tests, terminal typechecking and companion compilation. Eight new regression cases exercise all three Bridge doors, Gemini-to-Claude and Claude-to-Gemini switching, family edits, alias pinning, cooldown expiry, and in-flight selection changes. CodeRabbit reviewed all three implementation/test files with zero findings. Release packaging and four-platform binary smokes are required before publication.

Tests use synthetic upstream responses, not live quota. This change does not remove real provider rate limits or relax signed Claude launch-profile restrictions. Cooldowns use exact model IDs; if multiple models share an upstream quota bucket, another model can receive its own rejection before Wisp records its cooldown. No quota-group relationships are guessed.
