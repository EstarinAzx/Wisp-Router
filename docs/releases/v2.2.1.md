# Wisp 2.2.1 / companion VSIX 1.14.1

Fixes signed-in Codex desktop integration reducing native model capabilities when a shared Wisp route pointed at the same model name.

## What changes

- **Native models stay native.** Their complete catalog entries are retained, including Max/Ultra where advertised, multi-agent settings, instructions, tool support and context metadata. Wisp no longer replaces a native self-route with a reduced Alias descriptor.
- **Desktop native names use native sign-in and requests.** Native names take precedence over shared external overrides and Alias collisions. Those saved routes still work in other Wisp clients. To select Grok or another external model in desktop, use a distinct Alias such as `Grok 4.6 (Wisp)` rather than overriding a native model name.
- **Upgrades repair old catalogs.** Repeated `wisp codex-desktop enable`, as well as `refresh`, rebuilds the generated catalog from the saved full native snapshot. A native choice is no longer removed because a shared route targets an unsupported Provider.

Your configured context and compaction preferences are preserved. **This release does not unlock a full 1M usable context window.** Native Codex still applies its own model limits. On the tested Astra catalogs, requested 1000000/900000 resolves to 828400 usable context and a 784800 normal compaction threshold; these values describe the tested Codex builds, not a permanent Wisp limit.

Visible effort choices also depend on Codex desktop's own UI. In desktop 26.915.3509.0, its default allowed-effort list excludes Max even though the native catalog and app-server still advertise it. Ultra is visible and passed a live desktop reply check. Wisp preserves the metadata; it does not override that desktop UI filter.

## Upgrade

Desktop protocol **3** requires the updated setup command and serving Bridge. Update terminal/npm to **2.2.1** and companion to **1.14.1** if VS Code hosts your Bridge. Older protocol-2 hosts are refused. Restart Codex after changing its catalog/configuration; reload VS Code after updating the companion.

For an intact active installation, start the updated Bridge and run `wisp codex-desktop refresh` (or repeat `enable`). Native/account rediscovery still requires disable, native discovery, then enable. If you manually removed Wisp's config entries, inspect the ownership conflict before reactivation; do not restore an old config backup wholesale.

After publication:

```sh
npm i -g wisp-router@2.2.1
code --install-extension wisp-1.14.1.vsix
```

The release assets are `wisp-v2.2.1-win32-x64.exe`, `wisp-v2.2.1-darwin-arm64`, `wisp-v2.2.1-darwin-x64`, `wisp-v2.2.1-linux-x64`, and `wisp-1.14.1.vsix`. npm shell and platform package versions are **2.2.1**. **wisp-slot is unchanged.**

## Verification boundary

Regression coverage checks native descriptor preservation, routing/auth separation, legacy-client behavior and upgrades from reduced catalogs. Actual CLI 0.154.0 app-server checks use isolated synthetic keyed/xAI endpoints for text, follow-up, tools, native routing and cancellation. Copied binary/npm smoke checks exercise the packaged application. Separate context-accounting probes also checked the installed desktop helper 0.155.0-alpha.2.6 without live inference.

The user confirmed native Ultra and Max replies and the Grok 4.6 Alias tool/follow-up smoke test on the Windows 2.2.1 candidate. Max required a separate, user-authorized local Codex UI preference workaround; that workaround is not shipped by Wisp. They observed about 828K context in Traycer; Codex desktop did not expose that readout, so desktop context display is not claimed as visually verified. The installed desktop helper 0.155.0-alpha.9 separately passed an isolated 828400-context accounting check. Larger-context backend acceptance, installed VS Code extension-host behavior and Traycer GUI Aliases remain separate verification boundaries. Antigravity Aliases and unsupported external hosted tools remain unsupported.
