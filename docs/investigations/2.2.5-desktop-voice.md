# Wisp 2.2.5: Codex Desktop voice transport

Investigated 2026-09-18 against Wisp `8d7423a` (2.2.1/protocol 3), the actual installed Desktop helper **0.155.0-alpha.9**, and OpenAI source commit `6b9826e3aa83b1a5947db50f4332cb9c65f1b340`.

Acceptance update: after the user started the candidate and explicitly authorized the settings migration, supported disable/enable succeeded with model, effort, context preferences, routes and sign-ins preserved. The user confirmed live Desktop voice worked. This supersedes the pre-activation statements below; separate external-Alias voice/tool handoff and live stop/restart cycles were not individually reported.

Implementation follow-up: protocol4 call/sideband transport and reversible setup are now implemented on the unpublished `feat/2.2.5-compatibility` branch. `bun packages/tui/tests/nativeDesktopVoice.check.ts <codex.exe>` passed two full synthetic signaling/sideband/text/stop cycles on the actual helper and Bun1.4.2, with both upstream credential boundaries and exact restoration checked. Independent code review is clear. The current live Bridge/settings were not changed. Microphone/audio and real external-model voice handoff remain unverified. The original research and probe below describe the pre-fix behavior.

## Confirmed cause

Desktop inherits Wisp's custom model-provider URL for voice call creation. Wisp implements signed `/codex-desktop/v1/responses`, but no `/codex-desktop/v1/live` route. The user's screenshot is the resulting local 404. The installed helper independently emitted the exact failing path in an isolated experiment.

Adding a `/live` alias to the existing native Responses forwarder would be incorrect. Voice uses a different body, destination, response and subsequent WebSocket connection. Native model names and external Alias text turns must keep their current routing.

## Actual helper experiment

Run `python D:/wisp-voice-research-20260918/probe.py`. Evidence: sibling `results.json`; disposable homes and stderr logs are in `default/` and `override/`. The script is local research tooling, pinned to this machine's helper path. It uses synthetic ChatGPT and Bridge credentials, a local HTTP fixture, and a refusing proxy for non-local HTTP destinations. It requests no model turn, microphone access or real media connection. It returns a synthetic SDP answer and intentionally rejects the sideband handshake after observing it.

Observed exit 0 on 2026-09-18:

| Configuration in isolated home | Call request | Body | Headers observed |
| --- | --- | --- | --- |
| Wisp-shaped provider, no call override | `POST /codex-desktop/v1/live` | Multipart `sdp` + `session` | Synthetic native bearer/account **and** local `x-api-key` |
| Same provider, call override containing `/backend-api/codex` | `POST /backend-api/codex/realtime/calls?intent=quicksilver&architecture=avas` | JSON `{sdp, session}` | The same native credentials **and** local `x-api-key` |
| Both cases, local sideband override | WebSocket `GET /sideband/rtc_fixture` | Upgrade handshake | Native bearer **and** local `x-api-key` |

The override case used a loopback destination, not OpenAI. It proves that changing destinations preserves the local capability header. Directly applying the equivalent external override would transmit that header to the external destination. No real secret was sent by this experiment. Existing live Codex/Wisp config, auth and desktop state hashes were unchanged.

The test did not reproduce Grok vision, run the production Bridge, complete a WebSocket connection, hear audio, or establish provider entitlement. Its success proves the transport observations only.

## Primary-source explanation

- [`prepare_realtime_start`](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/realtime_conversation.rs#L1178) builds voice providers from the selected model provider. `experimental_realtime_webrtc_call_base_url` and `experimental_realtime_ws_base_url` replace URLs, retaining provider headers.
- [`RealtimeCallClient`](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/codex-api/src/endpoint/realtime_call.rs#L62) tests whether the base URL contains `/backend-api`. For that shape it sends JSON to `realtime/calls`; otherwise the v3/frameless parser uses multipart `live`. Backend calls add `intent=quicksilver&architecture=avas`.
- [`create_realtime_call_with_headers`](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/client.rs#L690) retains matching native authentication for sideband control. The call response needs SDP and a `Location` containing a call ID; the ordinary Responses forwarder's response allowlist does not include `Location`.
- [WebSocket client](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/codex-api/src/endpoint/realtime_websocket/methods.rs#L775) defaults WebRTC sideband to `https://api.openai.com/v1`; v3 resolves to `/v1/live/<call-id>`. Its header merge retains provider headers. Consequently the sideband also needs a deliberate credential boundary even if its default destination is already native.
- [Wisp route table](../../packages/core/src/bridgeServer.ts#L1042), [native forwarder](../../packages/core/src/codexDesktop.ts#L27), and [setup/recovery](../../packages/tui/src/codexDesktop.ts) establish the current local boundary and exact-setting ownership.

Official [Codex configuration documentation](https://learn.chatgpt.com/docs/config-file/config-reference) was opened during this investigation. It documents custom provider URLs/authentication but does not establish this private voice contract. The pinned source and actual helper experiment carry the voice claims. The source schema labels the realtime override settings experimental; helper-version regression coverage is necessary.

## Recommended next implementation experiment

Keep voice on native OpenAI services, with Wisp acting only as a narrowly scoped transport intermediary. External model selection continues to govern backing text/tool turns; it does not imply Antigravity or Grok becomes the native speech model. End-to-end external-model voice handoff remains an acceptance case.

1. **Use Codex's existing formatting instead of inventing a multipart translator.** In an isolated activation, point the call override at a dedicated loopback path containing `/backend-api/codex`. Point the sideband override at a separate authenticated loopback path. The proven helper behavior then emits native-shaped JSON and routes both connections through the credential boundary. This remains a candidate until the complete fixture passes.
2. **Add fixed-destination forwarding.** Forward the call only to `https://chatgpt.com/backend-api/codex/realtime/calls`, with supported query values, allowlisted native headers and a bounded JSON body. Forward SDP/status/`Location` faithfully. Strip the Bridge secret and arbitrary inbound headers; refuse redirects. A call ID is data, never a caller-chosen host/path. Preserve cancellation and safe errors.
3. **Cover the separate WebSocket path.** Authenticate the HTTP upgrade independently because Node's upgrade path does not run the ordinary HTTP route handler. Proxy only the expected call-ID path to the native sideband host, strip the local capability, and preserve subprotocol/frame/close behavior, flow control and cancellation. Choose the smallest supported transport available to both Node and packaged Bun after a runtime check; do not hand-write a WebSocket frame implementation. This dependency/runtime choice is still open.
4. **Extend ownership and recovery together.** Setup currently owns provider/catalog keys only. Adding realtime overrides requires matching discovery, profile-conflict checks, journal ownership, refresh/migration and exact disable restoration. Preserve user-owned overrides or report a concrete conflict; do not overwrite them. Existing protocol-3 journals must remain recoverable. Coordinate the Bridge/setup protocol so an old server cannot be paired with newly generated voice settings.

Alternative: direct native URL overrides are smaller but fail the demonstrated local-header boundary unless Codex can independently suppress provider headers for voice. A general catch-all proxy is unnecessary. A multipart adapter could serve the existing `/live` URL, but still needs sideband handling and adds parsing/translation ownership that the local backend-shaped URL can avoid.

## Acceptance before claiming voice compatibility

- Reproduce the screenshot-shaped request against the old route and prove the new isolated configuration reaches the native-shaped call fixture.
- Capture both HTTP and WebSocket upstream headers; the native bearer/account reach only fixed native destinations and the Bridge secret reaches neither.
- Test missing/wrong local secret, missing native authentication, redirects, malformed/oversized bodies, bad call IDs, native 401/429/5xx, missing `Location`, disconnect and cancellation.
- Complete an actual-helper fixture: call creation, SDP notification, successful sideband handshake/events, stop and a second start. The current probe stops before successful sideband establishment.
- Verify enable/refresh/disable, older journals, concurrent/unrelated config edits, user realtime overrides and old Bridge protocol refusal without touching live state.
- Finally verify Desktop microphone permission, audible exchange, stop/restart, signed-in account, native selection and external Alias backing-tool handoff. Preserve current routes, context/compaction settings and running Bridge until intentional activation. No audio success claim is justified by the local 404 disappearing alone.

No production files, installed packages, provider selections or live settings were changed. The existing Bridge on 41184 was not contacted or restarted.
