## Finding

**No image corruption, stale-image injection, or tool-result reassociation was reproduced in Wisp's signed Desktop -> xAI path.** An offline request through the production Bridge preserves two distinct valid PNGs byte-for-byte, including ordered image-bearing tool results. The reported visual misidentification remains unexplained; this result does **not** establish that xAI consumed the images or that the deployed runtime equals this source.

Reported symptom supplied by the coordinator: Grok describes a VS Code `AGENTS.md` screenshot while the thumbnail shows cropped white letters on black; Desktop displayed “Viewed an image.” Follow-up inspection by the coordinator located the exact local Desktop rollout and verified the image returned by the client tool. The outbound xAI request was not captured.

## Actual incident evidence, separate from the offline fixture

The coordinating investigator reports these targeted local observations from the failing Desktop turn:

- The user attachment and subsequent `view_image` result have identical SHA-256 fingerprints and decoded length: **6,349 bytes, 246x55 pixels**.
- Visual inspection shows only **“Respond to greeting”**, with no editor window or clock.
- Grok4.6 (Wisp) called the correct clipboard-image path, then produced the incorrect editor/screenshot description.
- Earlier images in the same thread are 30x40 and 22x139 pixels; their corresponding tool outputs also match their input-image fingerprints.

This rules out a wrong file or changed bytes at the observed client tool boundary. It does **not** prove what image bytes reached xAI, whether xAI accepted the tool-result image shape, or which context the model used. These are observations relayed by the coordinator, not images/logs inspected by this research fixture. ## Source trace

| Boundary | Observed behavior | Source |
|---|---|---|
| Signed Desktop HTTP | `/codex-desktop/v1/responses` requires the local secret; native names bypass translation, external Aliases select the Provider. | [bridgeServer.ts](../../packages/core/src/bridgeServer.ts), `handle`, `handleResponses` |
| Signed parser | `parseDesktopResponsesRequest` removes supported unused hosted-search declarations, then uses the strict Responses parser. It does not manipulate images. | [bridgeResponses.ts](../../packages/core/src/bridgeResponses.ts), `parseDesktopResponsesRequest` |
| Attachments | User `input_image` data URLs become ordered `contentParts`; base64, MIME and detail are validated. No resize, file read, image decode, image lookup, or image cache occurs here. | Same file, `content` inside `parseResponsesRequest` |
| Tool images | `function_call_output` and `custom_tool_call_output` accept text/image arrays. The parser requires a preceding matching `call_id` and rejects unmatched/duplicate outputs; each output gets its own normalized turn. | Same file, tool call/output branches |
| xAI executor | Maps `contentParts`, `images`, `toolCalls`, and `toolResults` through to `xaiStream`. | [bridgeServer.ts](../../packages/core/src/bridgeServer.ts), executor `id: 'xai'` |
| xAI client | Passes messages directly to `buildCodexResponsesBody`; transforms selected union tool schemas/arguments, not image content. `XaiMessage` omits `contentParts` in its local type, but structural typing does not remove runtime properties. | [xaiClient.ts](../../packages/core/src/xaiClient.ts), `XaiMessage`, `xaiResponsesRequest` |
| Responses builder | Emits tool images inside `function_call_output.output` as `input_image`; preserves call IDs. User `contentParts` retain order. Base64/MIME/detail are reconstructed unchanged. | [codex.ts](../../packages/core/src/codex.ts), `responsesContent`, `buildCodexResponsesBody` |
| xAI sanitizer/send | Sanitizer modifies only cache retention, proxy encrypted-content include, and minimal reasoning effort. It does not rewrite input. Grok4.6 goes to `https://api.x.ai/v1/responses`; builder sets `store:false`; no previous-response ID is forwarded. | [xai.ts](../../packages/core/src/xai.ts), `rewriteXaiResponsesPayload`, `xaiResponsesUrl`; [xaiClient.ts](../../packages/core/src/xaiClient.ts), fetch |

Prior images are correctly replayed when present in client history. Wisp does not infer which image is “current,” remove older images, or verify that a tool's result bytes match the path named in its arguments. It preserves the supplied association. Therefore a wrong file returned by the client can pass through perfectly; `call_id` correctness is not file-content correctness.

## First-party documentation

Read through Traycer's in-app browser on2026-09-18:

1. [xAI Image Understanding](https://docs.x.ai/developers/model-capabilities/images/understanding): documents `input_image` with a base64 data URL in user content, arbitrary image/text ordering, PNG/JPEG input, 20MiB per-image limit, and recommends disabling server-side request/response storage. Wisp's fixture uses that documented input shape and `store:false`.
2. [xAI Responses reference](https://docs.x.ai/developers/rest-api-reference/inference/responses), including its linked [Markdown export](https://docs.x.ai/developers/rest-api-reference/inference/responses.md): describes text/image prompts and the input string/array, but the inspected reference/export does not enumerate image-bearing `function_call_output.output` support or image `detail` values.
3. [xAI Function Calling](https://docs.x.ai/developers/tools/function-calling): inspected examples return serialized textual tool results. They do not establish whether image result arrays work. **Absence of an example is not proof of rejection or silent loss.**

Compatibility questions still open: Wisp permits `original` detail and PNG/JPEG/WebP/GIF, whereas the inspected image guide documents PNG/JPEG and shows `high`. Neither documentation nor this stub proves xAI accepts all Wisp-permitted values. A cropped screenshot in ordinary PNG with `auto`/`high` cannot be blamed on those gaps without its actual payload.

## Smallest next step and remediation boundary

Do not alter image serialization or discard prior history on this evidence. Keep this runnable fixture; a small xAI case in the existing Bridge tests can later make its transport assertions part of CI. Aligning `XaiMessage` with the shared message type would improve the type contract but would **not** fix the observed runtime symptom.

For a user-authorized live acceptance check, use harmless, readily distinguishable image fixtures (e.g. large red triangle and blue circle with unique labels), not the 2x2 transport PNGs as an OCR benchmark:

1. Fresh Desktop conversation: attach image A and request its color/shape/label. Repeat with B.
2. Same actual Grok model/endpoint: return B through `view_image`, including a prior A in history; ask specifically about the latest result. Then try a fresh conversation containing only the B tool result.
3. At client result -> Bridge ingress -> upstream egress, compare request-scoped item index, role, call ID, MIME, detail, decoded byte length, and image SHA-256. Hash before and after any client resize separately. Avoid recording raw images, prompts, auth headers, or local paths in routine logs.
4. If image hashes differ within Wisp, fix the first boundary that changes them and retain a failing fixture. If they are identical but tool-result vision alone fails, confirm the provider contract; only then consider a provider-specific adapter or explicit rejection. Moving images into a synthetic user message changes semantics and requires its own acceptance test.

Pass criterion: the correct latest image is identified across attachment and tool-result paths, with matching per-request image fingerprints and call association. Transport checks alone do not meet that live criterion. No production remediation is justified yet.
